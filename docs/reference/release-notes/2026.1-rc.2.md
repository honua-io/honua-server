# 2026.1-rc.2 identifier changes

This release candidate makes intentional breaking identifier changes before the first supported server release. Update integrations against the matching server contract and client versions. Earlier evaluation-build compatibility results do not qualify these changes.

The [Layer glossary](../../concepts/domain/layer.md) defines `storageLayerId`, `serviceLayerIndex`, and the graph Layer ID. For example, storage handle `41`, Service-local index `3`, and graph ID `roads:primary` can identify the same exposed Dataset. Rebinding that Layer to storage handle `73` preserves its public identity.

| Surface | Previous identifier | Identifier in rc.2 |
| --- | --- | --- |
| Connection-scoped layer administration | `layerId` | `storageLayerId` |
| Global `/api/v1/admin/metadata/layers` routes | Ambiguous `layerId`, sometimes resolved as a Service-local index | `storageLayerId`, resolved explicitly through the storage binding |
| Service-scoped layer administration | `layerId` | `serviceLayerIndex`, scoped by the Service |
| MCP query, map, style, discovery, and entity-resolution contracts | `layerId` | `serviceLayerIndex`, with the associated Service |
| WFS feature type local name | Resource name with a storage-derived suffix | Graph Layer ID encoded as an XML NCName |
| Service-scoped WMS layer name | Resource name or storage handle | The Layer's Service-local `Identifier.Value` |
| OGC API Records Service `properties.layerIds` | Storage handles | Graph Layer IDs |
| OGC API Records layer record ID | `layer:{storageLayerId}` | `layer:{graph Layer ID}` |
| Asynchronous export status | `layerId` with the requested Service-local index | `serviceLayerIndex` with the requested Service-local index |
| Public MapLibre style route | `/api/styles/{layerId}.json` with an integer selector | `/api/styles/{publicationId}.json` with the graph Layer ID |

Global metadata administration no longer substitutes a Service-local index for a storage handle. If multiple distinct Dataset resources claim the same storage handle, configuration writes fail as ambiguous rather than selecting one resource. SDK clients should regenerate against the updated OpenAPI parameter and model names.

MCP clients must send `serviceLayerIndex`, including entries in `render_map.layers`. Discovery and entity resolution return the explicit Service-local selector. The affected tools are `query_features`, `render_map`, `get_style`, `apply_style_preset`, `list_layers`, and `resolve_entity`.

Each routable graph Layer has its own WFS feature type, including Layers that share a Dataset. CITE fixture preparation authors the graph IDs required by the standards suites; prior CITE receipts do not qualify the new contract. WMTS legend links use the Service-local WMS identifier.

WFS uses the reversible `XmlConvert.EncodeLocalName` encoding of the graph Layer ID. Decode the advertised local name with the corresponding XML name decoder to recover the graph ID. Encoding preserves distinctions between IDs containing punctuation and IDs containing literal escape-shaped text. Different Services can both expose index `0` while retaining distinct WFS feature types through their globally unique graph IDs.

Use the identifiers advertised by capabilities, discovery, and record links. Storage handles are no longer accepted as public protocol aliases. Public style requests resolve the current storage binding of the identified Layer.

Follow the [migration guide](../../guides/migrate/public-layer-identifiers.md) to update stored selectors and client contracts.

Exports queued by earlier evaluation builds have no selector alias. A request with the previous persisted shape fails as missing request metadata when its progress is readable. If its progress is also unreadable, recovery removes the request and quarantines the progress from active indexes without inventing a Layer identity. Status and cancel return a record-specific conflict explaining that a new export request is needed; shared listings continue to show healthy operations.

Other client-visible behaviour clarified for rc.2 is in the [2026.1 rc.2 release notes](../rc2-release-notes.md).

## Upgrade from rc.1

Schema migrations are forward-only. Rolling rollback and N-1 reader compatibility are not supported. The following migrations deliberately break earlier readers; their exact SQL hashes and reasons are recorded in `eng/schema/schema-release-boundary.v1.json` for the existing N-1 gate machinery.

| Migration | Reason the previous reader is incompatible |
| --- | --- |
| 226 | Map/App draft identity fields and formats replace the previous envelope fields. |
| 227 | Deployment source kinds change to `map` and `app`. |
| 228 | Stored Map/App result identities and formats change. |
| 229 | Mutable Studio draft bodies adopt Map/App fields and formats. |
| 230 | Report Map embeds use `mapUri` in place of `mapPackageUri`. |
| 231 | App publication kinds and dependency kinds adopt canonical names. |

Back up the installed database, stop and drain previous nodes, then apply the upgrade with matching clients. Do not restart an older binary against the migrated database. Rollback requires restoring the pre-upgrade backup and matching binary. Installed-stack verification must exercise the forward migration, repeat application, canonical reads and preserved immutable history before this upgrade is qualified.

## Map and App identities

Map and App are the model names as well as the user terms. These are breaking changes for evaluation-build integrations; retired public names have no aliases.

| Surface | Previous name | Name in rc.2 |
| --- | --- | --- |
| .NET models | `MapPackage`, `AppPackage` | `Map`, `App` |
| JSON identities | `mapPackageId`, `appPackageId` | `mapId`, `appId` |
| Model formats | `honua_map_package.v1`, `honua_app_package.v1` | `honua_map.v1`, `honua_app.v1` |
| Deployment source kinds | `map_package`, `app_package` | `map`, `app` |
| Content publication kind | `generated-app` | `app` |
| Content dependency kinds | `resource`, `publication`, `map-package`, `app-package` | `dataset`, `layer`, `map`, `app` |
| Studio generation routes | `/api/v1/admin/studio/map-packages/generate`, `/api/v1/admin/studio/app-packages/generate` | `/api/v1/admin/studio/maps/generate`, `/api/v1/admin/studio/apps/generate` |
| Map publication route | `/api/v1/admin/packages` | `/api/v1/admin/maps` |
| Map publication body and response | `package`, `packageId` | `map`, `mapId` |
| MCP creation tools | `honua_create_map_package`, `honua_create_app_package` | `honua_create_map`, `honua_create_app` |
| MCP resources | `honua://map-packages/{packageId}`, `honua://app-packages/{packageId}` | `honua://maps/{mapId}`, `honua://apps/{appId}` |
| Plan analysis App preview | `appPackage` | `app` |
| Report Map embed reference | `mapPackageUri` | `mapUri` |

Upgrade the server, MCP contract and clients together. Back up the database and drain active work before applying migrations 232–237. These migrations update mutable draft envelopes, deployment source references, result references and report Map embeds. They preserve identity values, ownership, expiry, deployment revision values and opaque user payloads. Studio draft generations advance once when their envelope changes, so clients must reload drafts before editing. Conflicting old and new identities abort migration rather than choosing a value.

Published Studio versions, publication history and event records remain immutable. Reopening a historical Studio version creates a draft with canonical root identities and formats while preserving the original version bytes and content hash. Conflicting identities or malformed bodies fail reopening. Publication storage projects historical names into the canonical model when reading; new publication writes use canonical names. These private history readers do not accept retired names in public requests. Restoring the pre-upgrade database backup together with the matching server is the rollback procedure; an older server cannot safely read the migrated mutable records.

## Console catalog vocabulary

Console content now uses `dataset`, `map` and `app` as first-class kinds.
The previous `saved-map` and `generated-app` kinds are rejected; there are no
aliases. Update authored content payloads to `map` and `app`. Before upgrading
an evaluation build, export and delete existing Map and App records through
the existing server's content API; after upgrading, recreate them with the new
kinds. Console content is encrypted in the system database, so do not edit
encrypted database values. A server that starts with old-kind records cannot
list or delete Console content until it is restored from the pre-upgrade
backup, so do the export and delete first. This unreleased contract requires
matching Console and server versions.

| Previous name | Canonical name |
| --- | --- |
| `ConsoleContentItemType.SavedMap` / `saved-map` | `ConsoleContentItemType.Map` / `map` |
| `ConsoleContentItemType.GeneratedApp` / `generated-app` | `ConsoleContentItemType.App` / `app` |
| `ConsoleSavedMapTypeMetadata` | `ConsoleMapTypeMetadata` |
| `ConsoleGeneratedAppTypeMetadata` | `ConsoleAppTypeMetadata` |
| Layer sidecar `ResourceId` / `resourceId` | `DatasetId` / `datasetId` |

Published Dataset rows use `ConsoleContentItemType.Dataset` / `dataset` and
`ConsoleDatasetTypeMetadata`: `datasetId`, `kind`, optional `geometryType`,
and `fieldCount`. They are authorized through their exposed Layers, deduplicated
across Services and read-only in Console content CRUD. They expose neither
Connection credentials nor a guessed vector/raster kind for opaque tile data.

## Console discovery Environments

Discovery configuration uses `Console:CatalogDiscovery:Environments` and the `CatalogDiscoveryEnvironmentOptions` model. Registry JSON uses `environmentId` and `environmentName`; route parameters use `{environmentId}`. Update the matching Console client and configuration together. Keep existing ID, tenant and namespace values unchanged so existing discovery item handles remain stable. There are no retired-name aliases. Environment mappings retain the existing authorization and tenant/namespace checks.

## Forms route and operation names

Forms routes now name Forms directly: `/api/v1/admin/forms` for authoring and
`/api/v1/forms` for runtime access. The `/packages` segment is removed; Version
path parameters use `formVersion`. Public operation names drop `Package`, such as
`ListForms`, `CreateFormDraft` and `SubmitForm`. These are breaking renames with no
aliases. The [migration guide](../control-plane-migration-guide.md#forms-routes-and-operation-names)
lists every operation rename and the client regeneration requirements.

## Console Environment access

Console access responses rename `workspaceId` / `workspaceName` to
`environmentId` / `environmentName`; access routes name their parameter
`environmentId`. The URL shape and identifier values stay the same. Role scopes
are `environment`, `content`, `layer`, and `dataset-field`. The previous Environment override and overall assignment scopes are consolidated into Environment. The Layer scope replaces
`publication`, and `dataset-field` replaces `resource-field`. There are no
retired-name aliases. Update the Console client with the server.

A database migration gives each Console-created role the reserved ownership
grant `environment-membership` beside its existing `workspace-membership` grant.
Role IDs, names, memberships and other permissions are unchanged. The new server
reads and writes only `environment-membership`, so roles it creates or edits do
not carry the old grant and an older binary does not show them in Console.
Back up the database before upgrading, and roll back by restoring that backup
with the older binary.

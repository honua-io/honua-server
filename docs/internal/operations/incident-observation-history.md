# Incident observation history

Operational observations belong to an authority scope. The PostgreSQL observation journal retains immutable source evidence independently of inbox reads. Its key is the combination of authority scope, source identifier and source observation identifier. Repeated delivery returns the original observation, including its original timestamp, state and evidence. A later recovery or an unknown source state needs its own observation identifier.

Reads require an explicit authority scope, a lower timestamp bound and a limit from 1 through 1,000. Results are ordered by observation time descending, then source and observation identifier. An optional finding identifier narrows the history within that authority and time window. An optional inclusive upper timestamp bound excludes later recurrences when reading a historical episode. It must not precede the lower bound. The page reports the complete matching observation count before the limit, using the same database snapshot as the returned evidence, and reports truncation explicitly. The count measures recorded observations, not incident episodes or source completeness; a truncated page cannot establish recovery. Absence of an observation does not establish health. Evidence must be valid JSON with a maximum encoded size of 65,536 bytes.

An observation's finding identifier correlates evidence; it is not a verified incident episode identifier and must not authorize spending or other actions. A source collector must derive authority from its trusted server configuration and use stable delivery identifiers. Callers must not select another authority through request input. The store does not expose an HTTP endpoint or accept browser writes.

The CloudWatch alarm collector writes observations and updates persisted incident episodes before acknowledging a queued event; see [AWS operations events](aws-ops-events.md). The journal does not yet collect computed findings, resolve source freshness, enforce snooze policy or publish notifications. Existing investigation records remain the place for persisted diagnosis. No automatic retention deletion is enabled: removing old evidence requires an explicit retention policy that preserves active and unknown incidents and their action/audit references.

Migration `169_CreateOpsIncidentObservations.sql` adds the journal without changing existing findings or external-event identities. Deploy the migration before enabling a collector. PostgreSQL failure must leave collection unknown or failed; it must not produce a healthy status from an empty result.

Identity fields are nonblank and limited to 256 UTF-8 bytes each. Evidence is retained verbatim as JSON text.

The canonical incident context reader accepts an authority-scoped persisted episode identity and a bounded evidence limit. It returns null for a missing episode or the wrong authority. It preserves the episode's recorded state, lifecycle version and observation time; evidence is bounded by that episode's start and last observation, so a later recurrence cannot alter a closed episode's context. Missing and truncated evidence are explicit. Available evidence means the bounded journal page is present without truncation; it does not establish source completeness, current health, impact or cause. Database errors propagate rather than becoming empty or healthy results. Episode and evidence reads are separate snapshots; callers must use the returned episode version for action admission, never treat this context read as action authorization.

The read-only `GET /api/v1/admin/observability/incidents/{incidentId}` endpoint accepts an ops-read or full admin credential. Its authority is fixed by the server to `platform`; request input cannot select another authority. The optional `limit` bounds evidence from 1 through 1,000, defaulting to 100. The response includes the recorded episode, evidence availability, full matching observation count and read time. Affected scope, impact and cause confidence remain explicitly unknown until separately established. Read time does not refresh the episode’s observation time. Missing episodes return 404; persistence failures return a generic 503 without connection or SQL details. Responses bypass output caching. This endpoint cannot authorize an action.

Investigation links accept `resourceKind: "incident"` with an opaque resource identifier such as `incident:platform:<episode UUID>`. Pins accept `eventKind: "incident"` and can retain a particular recorded lifecycle version as `incident:platform:<episode UUID>:<version>`, with `occurredAt` set to the evidence observation time. Use the existing admin investigation endpoints to persist notes, links and pins; adding these annotations does not change the incident lifecycle, refresh evidence or establish cause. These references are operator annotations: the investigation API does not validate episode existence or confer authority through their text. Read the incident context separately to establish availability. The additive investigation constraint migration must be deployed before accepting incident references.

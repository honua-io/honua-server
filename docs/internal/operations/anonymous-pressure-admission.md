# Anonymous work during database pressure

Honua protects database headroom for signed-in requests when its local bounded database admission gate shows queue pain: at least as many queued requests as the gate has slots, or a queue at a gate that is at least 80% utilized while the average admission wait (immediate admissions count as zero) is 250 ms or more. A short queue at a busy gate is an ordinary burst and is served, not refused. Expensive anonymous requests receive the existing protocol-specific retryable service-unavailable response before tenant database access. The retry delay is one to three seconds, spread at random so refused clients do not return as one wave. Health, sign-in and metadata routes remain available. Under pressure, anonymous classic OGC POST requests are guarded conservatively because an XML body can override a metadata operation in the query string; use GET for metadata during that window. HEAD requests to expensive query routes receive the same guard as GET. Guarded work includes feature, item and record queries on every protocol (GeoServices, OGC API, STAC, OData, SensorThings, WFS, WMS and WMTS feature info), edits including attachment changes, exports, replica synchronization, geometry and network operations, processes and MCP calls. Tile requests are not guarded: they are served from the tile cache and CDN in normal operation, and refusing them would blank public maps; a cache miss still uses the ordinary bounded database gate.

This guard runs after authentication and before tenant context and schema resolution. It applies even when application request-rate limiting is disabled. It uses current resource pressure, so requests spread across many IP addresses still encounter the guard. No IP address counters or external coordination service are required.

Once the queue is shorter than the gate and either empties, or the average admission wait falls below 250 ms (or utilization falls below 80%), anonymous work resumes automatically. Earlier acquisition timeouts do not extend the denial window. Signed-in traffic still uses the ordinary bounded database gate; the guard reduces competition but does not guarantee successful queries during a database outage.

Edge rate limits and WAF protection remain deployment responsibilities. This guard makes no AWS changes and creates no automatic WAF rules. Any proposed WAF rule requires operator approval.

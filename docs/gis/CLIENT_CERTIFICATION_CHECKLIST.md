## Evidence for exclusions, skips and failures

Genuine N/A and skip outcomes are useful. Review their cause per operation:

| Reason | Evidence required | Disposition |
|---|---|---|
| Client does not support the operation | Version-matched vendor documentation or upstream source, covering applicable native providers and entrypoints | N/A for that client/version/operation |
| Required license is unavailable | Installed license/extension/portal-entitlement observation plus the precise vendor requirement, including service-backed exceptions | Valid licensed skip, disclosed as a limitation of the tested profile |
| Preview feature is not selected | Source maturity, configuration gate and declared profile selection | Retained in the separate readiness backlog |
| Server does not implement the operation | Exact candidate route/capability/implementation source plus configured runtime evidence; native reproducer and independent working control where available | Server capability gap, with scope and expected behavior stated |
| Harness fails or gives up | Runner error, documented or positive-control entrypoint, and repair/replay evidence | Open harness repair |
| Fixture, credentials or environment missing | Named missing prerequisite and retry conditions | Blocked or documented skip |

A disabled menu, missing provider key, unsuccessful URL, HTTP error, timeout or
empty result alone does not identify the cause. Check documented alternate native
paths and a working control before concluding client absence. A missing license
must not conceal a supported operation available at the installed license level.
A disabled server feature must not be described as unimplemented.

For a failed native workflow, retain the client build, exact entrypoint, license
state, request/response or correlated server trace, candidate/configuration,
independent expected result and reproducible failure. Public sample services are
read-only controls; edits and failure cases use owned fixtures. Manuals establish
paths and limitations, not successful Honua execution.

## Completion and validation

Certification is complete for a declared version/license/configuration profile
only after its inventory is reconciled, applicability is reviewed, every required
native child case passes, and the evidence join verifies the same frozen shipping
**NativeAOT/Production** candidate, client builds, fixtures and configuration.
Missing receipts, failed required cases, unresolved harness defects and stale
candidate bindings prevent that claim. Licensed skips and N/A are separately
reported limitations, never successful execution of those operations.

UI results require actual inspected UI evidence. ArcPy/PyQGIS, REST probes,
conformance suites, mocks and adapted/plugin paths retain their own identities.
A parent operation cannot inherit success from one passing child or tool alias.
Historical JIT receipts remain useful diagnostics and regression evidence.

`python scripts/certification/build-client-checklist.py --check` verifies tracker
structure and generated projection freshness. It does **not** resolve receipt
files, verify their hashes or certify a shipping candidate. The existing platform
[receipt verifier](../../scripts/certification/verify-client-certification-receipts.py)
and owner-native gates retain their own governed inputs; the four-client case
crosswalk and acceptance join remain explicit open work below.

Run `python scripts/certification/test_build_client_checklist.py` for tracker
regressions. Regenerate with `python scripts/certification/build-client-checklist.py`.
No new native passes or exclusions are awarded by this scope update.

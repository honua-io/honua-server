# Cloud-Native-Geospatial (CNG) Conformance — Status

Last reviewed: 2026-06-20
Owner: Honua Server platform

This page records how honua's **produced** cloud-native-geospatial artifacts are
validated against the canonical, first-party validators, and which formats are
intentionally out of scope. The functional lane lives at
[`.github/workflows/cng-conformance.yml`](../.github/workflows/cng-conformance.yml),
the runner at [`scripts/conformance/cng/run-cng-conformance.sh`](../scripts/conformance/cng/run-cng-conformance.sh),
the store-backed seed/compose under [`docker/cng/`](../docker/cng/), and the
artifact generator under
[`scripts/conformance/cng/artifact-gen/`](../scripts/conformance/cng/artifact-gen/).

## Gated formats

The lane fails CI if any validator exits non-zero against honua's real output.

| Format | honua surface | How it is produced for the lane | Canonical validator | Gate |
|---|---|---|---|---|
| **GeoParquet 1.1.0** | FeatureServer / MapServer `f=parquet` | Fetched live from the store-backed `cng` FeatureServer (`f=parquet`) | [`gpq validate`](https://github.com/planetlabs/gpq) | hard |
| **FlatGeobuf** | FeatureServer `f=fgb` | Fetched live from the `cng` FeatureServer (`f=fgb`) | GDAL `ogrinfo -al -so` with `OGR_FLATGEOBUF_VERIFY_BUFFERS=YES` (no dedicated validator exists) | **PENDING honua-server#1938** |
| **PMTiles v3** | `GET /api/v1/tiles/pmtiles/{artifactId}` | Generated by driving honua's `PMTilesWriter` | [`pmtiles verify`](https://github.com/protomaps/go-pmtiles) | hard |
| **3D Tiles 1.1** | `/scenes/.../tileset.json` (+ GLB content) | Generated by driving honua's `TilesetDocumentWriter` + `GeometryTileBuilder` | [`3d-tiles-validator`](https://github.com/CesiumGS/3d-tiles-validator), which chains the Khronos [`gltf-validator`](https://github.com/KhronosGroup/glTF-Validator) | hard |

### Store gating: root cause, fix, and the FlatGeobuf follow-up

The default `test` / `browser_compat` services returned
`HTTP 400 "Output format ... is not supported by the configured feature store"`
for `f=parquet` / `f=fgb`. Investigating against a freshly-built, PostgreSQL-backed
service showed this is **not** just the in-memory test store — it affects every
**source-backed (provider-routed)** layer:

- The FeatureServer gates `f=fgb` / `f=geobuf` on the resolved store implementing
  the `IFlatGeobufFeatureStore` / `IGeobufFeatureStore` marker interfaces.
- Every legacy `honua.layers` row compiled through the Metadata v2 compat
  snapshot (`honua.seed_metadata_v2_compat_snapshot`) is assigned a
  `primaryStorageBindingId`, so reads route through `FeatureProviderQueryRouter`
  -> `PostgresStorageMappedFeatureReader`.
- `PostgresStorageMappedFeatureReader` implements `IFeatureReader` /
  `IPagedFeatureReader` / `IStreamingFeatureStore` but **not** the FlatGeobuf /
  Geobuf markers (its `QueryFlatGeobufAsync` is a `NotSupportedException` stub),
  so the marker check fails and the handler returns 400 — even though the
  underlying PostGIS table supports `ST_AsFlatGeobuf`.

**GeoParquet fix (this PR).** `f=parquet` / `f=arrow` are encoded entirely in
managed code (`GeoParquetFeatureWriter` / GeoArrow formatter) from the
materialized `QueryResult<Feature>`, which **every** reader can produce — they do
NOT depend on a store-native encoder. The handler's parquet/arrow guard was
incorrectly reusing the FlatGeobuf marker as a proxy, so it 400'd parquet for the
whole source-backed surface. This PR removes that incorrect proxy guard
(`FeatureServerQueryHandler`), so `f=parquet` now works for source-backed layers;
`gpq validate` passes against the live output.

**FlatGeobuf follow-up (honua-server#1938).** Producing valid FlatGeobuf / Geobuf
from the storage-mapped reader needs native `ST_AsFlatGeobuf` / `ST_AsGeobuf`
aggregate SQL over the storage mapping — a larger change tracked in
honua-server#1938. Until it lands, the lane treats the `f=fgb` step as PENDING
(it records the 400 and the issue reference but does not fail the lane); flip it
to a hard gate once #1938 ships.

The lane seeds an additive, store-backed `cng` FeatureServer
(`docker/cng/seed.sql`, layer 1000 over the `features` table) so the cloud-native
export paths are exercisable end to end without disturbing the existing test
services.

## Carve-outs (intentionally NOT gated)

honua consumes/transcodes these formats but does not PRODUCE conformant output,
so gating a first-party producer-validator against them would be meaningless:

- **COG** — `exportImage` emits a plain GeoTIFF; `format=cog` is rejected. honua
  reads COG, it does not author cloud-optimized GeoTIFF output.
- **Zarr / GeoZarr** — read / transcode only.
- **COPC** — read / transcode only.

## Local validation evidence (2026-06-20)

Running honua's writers through their canonical validators on the produced
artifacts:

- GeoParquet (`GeoParquetFeatureWriter`): `gpq validate` — **Passed 20 checks**.
  Live: after the parquet-guard fix, `f=parquet` from the source-backed `cng`
  FeatureServer returns 200 and validates.
- PMTiles v3 (`PMTilesWriter`): `pmtiles verify` — **exit 0**.
- 3D Tiles GLB (`GeometryTileBuilder`): Khronos `gltf_validator` —
  **Errors: 0, Warnings: 0**.
- FlatGeobuf (`f=fgb`): blocked on honua-server#1938 (storage-mapped reader does
  not yet emit FlatGeobuf); lane step is PENDING until the fix lands.

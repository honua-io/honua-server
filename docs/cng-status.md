# Cloud-Native-Geospatial (CNG) Conformance — Status

Last reviewed: 2026-09-07
Owner: Honua Server platform

This page records how honua's **produced** cloud-native-geospatial artifacts are
validated against the canonical, first-party validators, and which formats are
intentionally out of scope. The functional lane lives at
[`.github/workflows/cng-conformance.yml`](../.github/workflows/cng-conformance.yml),
the runner at [`scripts/conformance/cng/run-cng-conformance.sh`](../scripts/conformance/cng/run-cng-conformance.sh),
the store-backed seed/compose under [`docker/cng/`](../docker/cng/), and the
artifact generator under
[`scripts/conformance/cng/artifact-gen/`](../scripts/conformance/cng/artifact-gen/).

## Gated formats

The lane fails CI if any validator exits non-zero against honua's real output.

| Format | honua surface | How it is produced for the lane | Canonical validator | Gate |
|---|---|---|---|---|
| **GeoParquet 1.1.0** | FeatureServer / MapServer `f=parquet` | Fetched live from the store-backed `cng` FeatureServer (`f=parquet`); emits a GeoParquet 1.1 `covering.bbox` column for spatial pruning | [`gpq validate`](https://github.com/planetlabs/gpq) | hard |
| **FlatGeobuf** | FeatureServer `f=fgb` | Fetched live from the `cng` FeatureServer (`f=fgb`) | GDAL `ogrinfo -al -so` with `OGR_FLATGEOBUF_VERIFY_BUFFERS=YES` (no dedicated validator exists) | hard |
| **PMTiles v3** | `GET /api/v1/tiles/pmtiles/{artifactId}` | Generated by driving honua's `PMTilesWriter` | [`pmtiles verify`](https://github.com/protomaps/go-pmtiles) | hard |
| **3D Tiles 1.1** | `/scenes/.../tileset.json` (+ GLB content) | Generated by driving honua's `TilesetDocumentWriter` + `GeometryTileBuilder` | [`3d-tiles-validator`](https://github.com/CesiumGS/3d-tiles-validator), which chains the Khronos [`gltf-validator`](https://github.com/KhronosGroup/glTF-Validator) | hard |
| **COG tile transcode** | `GET /cog/.../{z}/{y}/{x}` (`CogTileResolver`) | `artifact-gen` drives `CogMetadataExtractor` + `TileDecompressor` + `CogTiffTileEncoder` over the canonical Web Mercator COG using HTTP range reads | `rasterio` window read against the fixture's declared sample formula, `rio-cogeo cog_validate(strict=True)`, `gdalinfo` | hard |
| **Zarr subset decode** | OGC Coverages / Zarr tile read (`ZarrSubsetReader`) | `artifact-gen` drives `ZarrMetadataExtractor` + `ZarrSubsetReader` over the canonical store using HTTP range reads | `numpy` against the declared formula **and** `xarray`'s own slice of the same store | hard |

### Store gating: root cause, fix, and the FlatGeobuf follow-up

The default `test` / `browser_compat` services returned
`HTTP 400 "Output format ... is not supported by the configured feature store"`
for `f=parquet` / `f=fgb`. Investigating against a freshly-built, PostgreSQL-backed
service showed this is **not** just the in-memory test store — it affects every
**source-backed (provider-routed)** layer:

- The FeatureServer gates `f=fgb` / `f=geobuf` on the resolved store implementing
  the `IFlatGeobufFeatureStore` / `IGeobufFeatureStore` marker interfaces.
- Every legacy `honua.layers` row compiled through the Metadata v2 compat
  snapshot (`honua.seed_metadata_v2_compat_snapshot`) is assigned a
  `primaryStorageBindingId`, so reads route through `FeatureProviderQueryRouter`
  -> `PostgresStorageMappedFeatureReader`.
- `PostgresStorageMappedFeatureReader` implements `IFeatureReader` /
  `IPagedFeatureReader` / `IStreamingFeatureStore` but **not** the FlatGeobuf /
  Geobuf markers (its `QueryFlatGeobufAsync` is a `NotSupportedException` stub),
  so the marker check fails and the handler returns 400 — even though the
  underlying PostGIS table supports `ST_AsFlatGeobuf`.

**GeoParquet fix (this PR).** `f=parquet` / `f=arrow` are encoded entirely in
managed code (`GeoParquetFeatureWriter` / GeoArrow formatter) from the
materialized `QueryResult<Feature>`, which **every** reader can produce — they do
NOT depend on a store-native encoder. The handler's parquet/arrow guard was
incorrectly reusing the FlatGeobuf marker as a proxy, so it 400'd parquet for the
whole source-backed surface. This PR removes that incorrect proxy guard
(`FeatureServerQueryHandler`), so `f=parquet` now works for source-backed layers;
`gpq validate` passes against the live output.

**FlatGeobuf follow-up (honua-server#1938).** Producing valid FlatGeobuf / Geobuf
from the storage-mapped reader needed native `ST_AsFlatGeobuf` / `ST_AsGeobuf`
aggregate SQL over the storage mapping, tracked in honua-server#1938.

> **Corrected 2026-09-07 (honua-server#4398).** This page previously said the
> FlatGeobuf step "records the 400 and the issue reference but does not fail the
> lane". That has not been true for some time: `validate_flatgeobuf` in
> `run-cng-conformance.sh` sets `FLATGEOBUF_STATUS=1` on any non-200 response, and
> that variable is included in the lane's overall gate loop, so a `f=fgb` failure
> **does** fail the lane. The table above now reads `hard` to match the code.

The lane seeds an additive, store-backed `cng` FeatureServer
(`docker/cng/seed.sql`, layer 1000 over the `features` table) so the cloud-native
export paths are exercisable end to end without disturbing the existing test
services.

## Carve-outs (intentionally NOT gated)

honua consumes/transcodes these formats but does not PRODUCE conformant output,
so gating a first-party *producer*-validator against them would be meaningless:

- **COG** — `exportImage` emits a plain GeoTIFF; `format=cog` is rejected. honua
  reads COG, it does not author cloud-optimized GeoTIFF output. What **is** gated
  is the tile transcode: `CogTiffTileEncoder` packages a decoded tile as a
  single-tile GeoTIFF, and that artifact is held to the canonical validators.
- **Zarr / GeoZarr** — read / transcode only. What is gated is the decoded
  subset `ZarrSubsetReader` returns, not a Zarr store honua wrote.
- **COPC** — read / transcode only; no honua-produced artifact exists, so no cell.
- **HDF5 / netCDF** — input-only diagnostic. `canonical.nc` is written by
  `xarray.to_netcdf` and honua has no reader in that loop, so its cells remain
  structurally incapable of passing.

### What the canonical-artifact validator can and cannot claim (honua-server#4398)

`scripts/conformance/cng/validate-canonical-artifacts.py` reads a wider artifact
set than the four gated formats above, and **not all of it has Honua code in the
producing loop**. This distinction is what decides whether a cell can be cited as
evidence for a Honua cloud-native claim, so it is now recorded in the fragment
itself rather than only in this page:

| Artifact | Producer | `honua_in_loop` |
|---|---|---|
| `cng.parquet` | live server, `f=parquet` | `true` |
| `cng.fgb` | live server, `f=fgb` | `true` |
| `honua.pmtiles`, `3dtiles/` | `artifact-gen` driving Honua's writers | `true` |
| `honua.cog.tif` | `artifact-gen` driving `CogMetadataExtractor` + `CogTiffTileEncoder` | `true` |
| Zarr subset in `honua-consumer-evidence.json` | `artifact-gen` driving `ZarrSubsetReader` | `true` |
| `canonical.webmercator.cog.tif` | `rio_cogeo.cog_translate` | **input, not evidence** |
| `canonical.zarr` (store cells) | `xarray.to_zarr` | **`false`** |
| `canonical.nc` | `xarray.to_netcdf` | **`false`** |

The `false` rows are Python validating Python's own output. The validator refuses
them a `pass` **structurally** (`ARTIFACT_PRODUCERS` /
`ARTIFACT_PRODUCER_OVERRIDES` -> `_apply_producer_attribution`), so no future
change to a validator body can turn them green and no consumer of
`protocol-certification-fragment.json` can mistake them for Honua evidence.
Attribution is recorded per **cell** (`surface/operation/client`), not per surface,
because the Zarr surface is mixed: its store-read cells are third-party while its
`subset-transcode` cell is Honua's.

**How COG and Zarr became Honua cells.** The direction is inverted rather than the
cells removed. `rio_cogeo` and `xarray` still write the fixtures, but they are now
*inputs*: `artifact-gen` serves them from a range-capable HTTP origin and drives
Honua's production readers over them.

- `canonical.webmercator.cog.tif` (EPSG:3857, 512x512, 256px blocks,
  `value(row, col) = row * 512 + col`, nodata at `(3, 7)`) is read by
  `CogMetadataExtractor`, its base-level north-west tile decoded by
  `TileDecompressor` and re-encoded by `CogTiffTileEncoder` into `honua.cog.tif`.
  The COG cells validate that file. The oracle is recomputed from the formula, not
  snapshotted: a transcode that dropped the predictor, cut the wrong tile or lost
  the nodata tag fails on exact pixels, not on a checksum.
- The canonical Zarr store is read by `ZarrMetadataExtractor` +
  `ZarrSubsetReader` for `temperature[1:3, 2:6, 4:12]` — a request that starts and
  stops off a chunk boundary on every axis, so a reader that widened it to whole
  chunks returns the wrong shape. The decoded samples are checked against the
  fixture's declared formula **and** against xarray's own slice of the same store.
  The store is written with the `zlib` codec because Honua's AOT-safe subset
  reader implements the uncompressed and zlib/gzip codecs; a fixture it could not
  decode would silently return the cells to third-party evidence.

**Range efficiency is measured, not asserted.** The HTTP origin in
`scripts/conformance/cng/artifact-gen/CountingRangeHttp.cs` records, per object
key, how many requests Honua issued, how many carried a byte range, how many
pulled a whole object, and how many bytes crossed the wire; a range that spans the
entire object counts as a whole-object download, not as a partial read.
`honua-consumer-evidence.json` carries those counters into `observed_transfer`,
where `_evaluate_budget` holds them to the profile. The COG budget is
`min_range_requests >= 1` and `max_full_object_downloads == 0`, so an
implementation that downloaded the object and sliced it locally — producing a
byte-identical tile — fails the cell. The Zarr budget adds chunk pruning: the
subset must touch 8 of the array's 32 chunk objects.

**Cells that did not run are reported.** A validator that threw before reaching a
client used to leave the identity simply absent from the fragment, which is
indistinguishable from a pass to anything counting passes.
`_append_unexecuted_cells` now emits an explicit non-passing row for every
governed identity that produced no observation, and the fragment carries a
`cell_receipt` block (`governed_cells`, `executed`, `passed`, `not_run`).

### Budget profiles are now evaluated

`FORMAT_BUDGET_PROFILES` declares the per-format oracles (`expected_metadata`) and
the range-efficiency budgets (`min_range_requests`, `max_full_object_downloads`,
`max_requests`, `max_transferred_bytes`). Until honua-server#4398 **nothing read a
profile to compare anything** — the only consumer was a self-test asserting the
profiles existed — and every governed row was rewritten `pass` -> `skip` with one
generic gap string.

`_evaluate_budget` is now that consumer:

- validators record what they actually read back (`observed_metadata`), and it is
  compared key-by-key against the declared `expected_metadata`;
- rows whose facets include `range-efficiency` additionally require a measured
  `observed_transfer` (requests, bytes, range requests, full-object downloads);
- a row that meets every declared budget **passes** and carries a real
  `evidence_digest`; a row that does not carries the precise unmet budget as its
  `skip_reason`, not the blanket `BUDGET_EVIDENCE_GAP`.

The observation must be read from the format Honua actually emits
(honua-server#4479). The GeoParquet cell originally read `crs` and `bbox` straight
off the geometry column metadata, neither of which `GeoParquetFeatureWriter` writes
for a 4326 layer: it omits `crs` because the GeoParquet default *is* OGC:CRS84, and
it declares a `covering` descriptor addressing a physical `bbox` struct column
instead of a metadata `bbox`. Read literally, the governed GeoParquet row observed
`None` / `[]`, missed its declared oracle every run and was rewritten to `skip` with
its evidence digest stripped. The validator now resolves the omitted default CRS and
aggregates the bounds out of the declared covering column.

### What remains candidate-bound

The lane can be dispatched against an exact candidate image — `workflow_dispatch`
validates `server_image` against `@sha256:[0-9a-f]{64}$` and requires `source_sha`
and `candidate_cut_at` — but nothing calls it that way. The caller belongs to the
cut runbook in `honua-release` and cannot be exercised before a candidate exists,
so on the weekly schedule the lane still builds locally and records
`docker image inspect --format '{{.Id}}'`, a local image id rather than a registry
digest. The receipt half of that requirement (which cells executed, with skipped
cells reporting as non-passing) is in place today.

The validator's own tests (`test_validate_canonical_artifacts.py`) were in no
`testpaths` and in no workflow. They now run as the `validator-selftest` job in
`cng-conformance.yml`, on every change to `scripts/conformance/cng/**`, and the
heavyweight lane job `needs:` them. That cheap job and the heavyweight lane sit in
**separate concurrency groups** (honua-server#4479): both are reachable on
`refs/heads/trunk`, and with one shared group and `cancel-in-progress` a push
touching the lane paths cancelled an in-flight scheduled run whose result the
replacement push run — which skips the `cng` job entirely — could not reproduce.

## Local validation evidence (2026-09-07, honua-server#4398)

Honua's consumer path, run on a native Windows host against the canonical
fixtures with the pinned clients:

- `CogMetadataExtractor` + `CogTiffTileEncoder` transcoded the base-level
  north-west tile of `canonical.webmercator.cog.tif` in **8 HTTP requests, 8 of
  them ranged, 0 whole-object downloads, 82,420 of 360,368 bytes**.
- `rasterio` read `honua.cog.tif` back as EPSG:3857, 256x256, 1 band, nodata
  -9999.0, bounds `[-20037508.342789244, 0.0, 0.0, 20037508.342789244]`, and its
  pixels matched the independently computed `row * 512 + col` array **exactly**
  (0 mismatches of 65,536).
- `rio_cogeo.cog_validate(..., strict=True)` returned `(True, [], [])` on the
  transcoded tile.
- `ZarrSubsetReader` returned `temperature[1:3, 2:6, 4:12]` as shape `[2, 4, 8]`
  `<f4`, touching **8 of 32 chunk objects**, and every sample matched both the
  declared formula and xarray's slice.
- `python3 -m unittest discover -s scripts/conformance/cng -p 'test_*.py'` —
  **31 passed**.
